# FDE 交付方法：从问题发现到可复制部署

FDE 的角色不是替客户堆叠 prompt 或一次性连接器，而是把业务目标转成可运行、可验证、可运营的 Harness 组合。成功标准是客户团队能够理解系统做什么、哪些动作必须由人确认、失败时如何接管，以及下一位工程师如何继续维护。

## 五阶段交付

```mermaid
flowchart LR
  discovery[1. 发现] --> design[2. 联合设计]
  design --> pilot[3. 受控试点]
  pilot --> operate[4. 运营化]
  operate --> productize[5. 产品化]
```

| 阶段 | 目标 | 主要产物 | 退出条件 |
| --- | --- | --- | --- |
| 发现 | 确认一个真实、反复发生且成本可量化的问题。 | 流程地图、用户角色、基线指标、系统与数据清单、风险清单。 | 双方同意一个可在数周内验证的工作流。 |
| 联合设计 | 定义输入、输出、授权、异常与人工接管。 | 服务/Provider/Consumer 划分、数据分类、审批矩阵、验收用例。 | 所有高影响动作均有最终授权点和回退路径。 |
| 受控试点 | 在有限用户、数据范围和动作范围中取得真实证据。 | 最小 Bundle/Preset、真实集成、观测面板、运行手册。 | 相对基线产生可复核改进，且失败不会扩大影响。 |
| 运营化 | 使系统能由客户日常使用和维护。 | 监控、告警、权限管理、支持流程、变更和发布机制。 | 客户能处理常见错误、审批和配置变更。 |
| 产品化 | 将重复出现的交付内容沉淀为标准产品单元。 | 通用 Service Definition、可配置 Provider、模板、测试集和文档。 | 新客户主要通过配置与已验证适配器上线。 |

## 发现阶段要问的问题

先观察真实工作，而不是先收集“希望 agent 能做什么”。FDE 应建立从触发到结果的事实链：谁发起、用了哪些系统、等待在哪里、什么结果算正确、错了怎样发现、谁能批准最终动作、数据是否允许进入模型。

优先选取具备以下特征的第一条流程：发生频率高、有明确输入和完成标准、输出可由领域人员快速复核、失败影响可控、可取得基线数据。不要把“完全自动化所有工作”作为试点目标。

## 把客户语言翻译为工程对象

| 客户表述 | FDE 需要补全的工程问题 | 常见 Harness 落点 |
| --- | --- | --- |
| “帮我查清楚发生了什么” | 哪些数据源是权威的？时间范围、租户和敏感字段如何限制？ | 只读 Service Provider + 查询工具 + Session 回放。 |
| “让它自动处理” | 是建议、草稿、可撤销写入还是不可逆写入？谁审批？ | 工具策略 + approval + Provider 幂等与审计。 |
| “需要每天持续做” | 是会话提醒、后台任务还是外部调度？冷启动如何处理？ | Schedule、Job、Workflow 或企业调度器。 |
| “多人一起用” | 用户、角色、租户、会话、工作区怎样隔离？ | 已认证入口 + 领域授权 + Preset/部署配置。 |
| “输出不稳定” | 目标是否可判定？是否缺少上下文、工具、验收或人工反馈？ | 结构化输出、工具结果、Skill、评估样本和反馈闭环。 |

## 受控试点的最小闭环

试点至少包含：一个真实入口、一个已认证身份、一个只读或低风险 Provider、一个明确模型工具、一个审计记录、一个失败可见面和一位业务 owner。没有这些要素的演示只能说明模型能对话，不能证明可交付。

把每次运行分为四个可观察点：输入是否被接收，模型是否获得足够上下文，工具是否在授权范围内执行，结果是否被业务人员接受。若结果不被接受，应记录原因属于数据、规则、模型理解、工具执行、授权等待还是产品交互，而不是笼统归为“模型不够好”。

## 与客户共同运营

建立每周节奏：审查成功率和人工接管样本，抽查被拒绝或被撤销的动作，复盘长耗时和 Provider 故障，决定一个可验证改进。把用户反馈转换为具名变更：新增数据字段、修正工具约定、收紧权限、改进提示词 section，或增加测试场景。

FDE 应维护三份运行材料：面向业务人员的操作与升级路径、面向客户管理员的配置与权限说明、面向工程师的集成与故障排查手册。三者不能用一份技术设计文档替代。

## 避免交付债务

不要为单个客户修改核心 loop、复制一套 Provider、把密钥放入 YAML、把客户规则写死在 prompt，或依赖 FDE 手工运行才能正确。这些做法会让第二个客户的成本高于第一个客户。

每次定制都应归类为四种去向：客户专属配置、可复用 Preset/Skill、通用 Provider、待验证实验。只有已有两个以上真实消费者且接口稳定的内容才进入通用产品层。暂时不抽象是可接受的，但必须把临时实现的 owner、限制和升级条件写清楚。
