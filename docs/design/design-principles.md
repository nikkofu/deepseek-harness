# 设计原则：把业务需求放到正确边界

本页给出二次开发时的架构判断准则。它补充[系统架构](architecture.md)，不替代仓库的[防御性模式](../defensive-patterns.zh.md)、[包约定](../../packages/AGENTS.md)或[扩展实操手册](../cookbook/extension-cookbook.zh.md)。

## 先分清四类信息

| 信息 | 归属 | 示例 | 处理方式 |
| --- | --- | --- | --- |
| 对话事实 | Session 事件日志 | 用户请求、模型回复、工具调用、审批结果。 | 可回放、可投影；模型可见内容必须可重建。 |
| 领域事实 | 领域存储或权威外部系统 | 客户、工单、合同、库存、配置版本。 | 由业务服务拥有 schema、权限、事务和保留期。 |
| 执行状态 | Job、Workflow、Subagent 或 Provider 生命周期 | 正在执行的导入、后台分析、子 agent。 | 具有明确 owner、取消、超时、资源释放和观察入口。 |
| 部署策略 | Bundle、Profile、配置和凭据引用 | 默认模型、工具开关、数据源路由、权限级别。 | 可配置、可审计、不得把密钥或客户数据写入代码。 |

最常见的失误是把这四类信息混在工具参数、全局变量或 prompt 中。混合会使恢复、审计、并发控制和客户隔离变得不可证明。

## 用“能力 seam”而不是“万能工具”接入业务

一个业务连接应先定义面向消费者的稳定动作，而不是先暴露底层 REST 端点。举例来说，“读取已授权项目的客户摘要”和“创建需审批的跟进任务”是稳定业务动作；它们背后的 CRM、数据仓库或工单系统可以替换。

```text
业务 Consumer（工具、UI、工作流）
        ↓
Service Definition（领域动作、结果、错误、授权上下文）
        ↓
Service Provider（API/数据库/队列适配、认证、限流、重试）
        ↓
权威业务系统
```

Service Definition 不应泄漏某个 Provider 的分页 token、HTTP 细节或 SDK 类型。Consumer 不应决定 Provider 的重试、凭据或连接池。Provider 不应自行定义模型如何理解结果。

## 把授权置于执行点

模型、提示词、UI 按钮和工具描述都只是引导，不是最终执行授权。涉及写入、外部通知、删除、批量操作、费用或敏感数据的动作，应在工具执行前和 Provider 执行前使用相同的业务授权事实。

推荐把动作分为四级：

| 级别 | 例子 | 默认交互 |
| --- | --- | --- |
| 查询 | 读取一条已授权记录、生成摘要。 | 直接执行，记录访问范围。 |
| 建议 | 生成草稿、变更计划、风险说明。 | 只产生候选内容，不写外部系统。 |
| 可撤销写入 | 创建草稿、增加标签、提交待审批项。 | 明确用户确认或策略自动批准，保留操作 id。 |
| 不可逆或高影响写入 | 发布、删除、批量变更、资金和权限动作。 | 强制审批、限制批量、幂等键、审计和人工回退。 |

Harness 已有的 sandbox、approval、permission preset 和 `tools/pre-execute` 是承载机制；客户业务授权规则仍须由领域插件和权威系统共同实现。

## 用事件表达事实，用投影表达视图

Session 日志适合记录“这次 agent 工作发生了什么”。它不适合承担跨客户报表、全局搜索索引或业务对象关系。将对话中需要持久解释的事实写入 SessionEventMap；将列表、状态面板、会话标题和检索结果作为投影；将跨会话领域对象放到 storage 或外部数据库。

事件处理要保持单向：先提交权威事实，之后才更新缓存、UI 或通知。任何订阅者失败都不应使核心生命周期卡住。由同一事实生成多个投影时，避免每个界面自行推断状态。

## 让长流程显式拥有生命周期

对短而确定的单次调用，工具 Provider 已足够。对会持续数秒以上、可取消、可重试或需要并行分工的工作，选择专用执行模型：

| 情形 | 选择 | 原因 |
| --- | --- | --- |
| 可观察后台单元 | `ctx.jobs` | 统一列出、读取、停止后台工作。 |
| 多 agent 编排 | `ctx.workflowEngine` + `ctx.subagents` | 工作流拥有并发、结果和总量上限。 |
| 需要连续沟通的子任务 | continuable subagent | 子会话具有稳定身份与消息续接。 |
| 单次复用父历史的检查 | fork 型一次性 subagent | 复用完成历史，但不引入持续子会话。 |
| 会话内的未来提醒 | Schedule | 状态进入原 Session 日志，Agent 恢复后处理逾期项。 |

worker thread 隔离宿主事件循环，不是安全边界。对不可信脚本、命令和数据源仍需要沙箱、权限、资源限制和 Provider 侧校验。

## 接口和错误要面向业务操作

每个公开动作都应说明：输入范围、授权主体、是否产生外部副作用、幂等性、超时和取消语义、可观察结果、可恢复路径。错误应区分无权、找不到、冲突、输入无效、上游暂时故障和永久拒绝；不要把原始 Provider 异常当作产品 API。

模型看到的诊断只应包含完成任务所需的概念。内部服务名、隐私字段、连接串和调试堆栈不应进入工具结果或提示词。

## 为替换而设计，但只抽象已有变化

先以一个真实 Provider 和一个真实 Consumer 验证接口，再在第二个实现或第二个消费者确实出现时抽出 seam。提前设计“通用业务平台”通常会把当前客户需求伪装成大量不可验证的选项。反过来，一旦模型工具、Web UI 和后台工作需要同一业务动作，就必须把实现从任一消费者中移出。

配置字段只能表达会随部署变化且可验证的选择，例如 Provider 路由、超时、批量上限、允许的工作区或默认模型。安全不变量、协议常量和授权判定不应降级为可随意关闭的开关。
