# 创业与产品化策略：用 Harness 建立可复用优势

DeepSeek Harness 更适合构建“有业务系统连接、可执行、可审计”的 agent 产品，而不是只提供一个通用聊天界面。创业团队的优势来自对一个工作流的理解、与真源系统的可靠连接、权限与人工协作设计，以及将这些能力压缩成可配置交付单元。

## 选择切入点

优先选择存在明确业务 owner 的工作流。它应具备高频或高价值、可取到权威数据、结果能被业务人员判断、自动动作可分级、上线后能度量收益这五个条件。模型生成质量不是唯一门槛；没有可信数据、权限和采用路径的场景不能因为演示吸引人就进入产品承诺。

| 选择问题 | 好信号 | 风险信号 |
| --- | --- | --- |
| 问题是否真实反复发生？ | 有可观察的工单、报表、等待时间或人工步骤。 | 只有“希望用 AI”的抽象愿望。 |
| 结果是否可验收？ | 有领域专家、业务规则或系统状态可核验。 | 只能依赖主观“回答像不像”。 |
| 数据能否安全接入？ | 权威系统有稳定 API、最小权限和明确 owner。 | 只能导出不受控副本或共享管理员账号。 |
| 写入是否可控？ | 能先做建议/草稿/审批，再逐步升级。 | 首期即要求不可逆批量自动化。 |
| 是否可复制？ | 多个客户共享同一领域动作和接入模式。 | 每个客户都需要改核心流程与数据模型。 |

## 产品结构：核心、适配、配置

```text
平台核心：Session、Agent、工具策略、权限、观测、部署与客户端
可复用领域层：Service Definitions、通用工具、审计模型、评估样本
客户适配层：Provider、身份映射、字段映射、审批规则、数据范围
客户配置层：Profile、Bundle patch、Preset、Skill、默认模型与限额
```

平台核心的改变最少，领域层在多个客户验证后演进，客户适配层隔离外部系统差异，配置层表达部署选择。这个分层避免“每次售前承诺都变成核心分支”。

## 从服务到产品的沉淀规则

| 出现的情况 | 应沉淀到哪里 |
| --- | --- |
| 同一客户的环境、范围或默认值变化 | 配置、Profile patch 或用户设置。 |
| 同一类用户需要不同工具和提示词 | Agent Preset、Skill 或 UI 配置。 |
| 多个客户接入同一类外部系统 | Provider 与其部署配置。 |
| 多个 Consumer 需要同一领域动作 | Service Definition 和通用领域包。 |
| 尚未验证、只服务一次交付的逻辑 | 客户适配层，注明 owner 和升级触发条件。 |

不要把“可配置”误当作产品化。一个配置项需要明确的取值、默认值、验证和实际消费者；否则它只是把决策转嫁给部署者。

## 商业与交付节奏

建议采用“设计伙伴—可验证试点—受控扩展—标准化上线”的节奏。设计伙伴提供真实流程、可用数据和每周反馈；试点证明一个可量化结果；受控扩展增加用户、数据源或低风险动作；标准化上线才承诺 SLO、权限模型、支持和迁移策略。

收入模型应与持续价值和责任边界匹配。实施服务可以覆盖集成与流程设计，订阅或用量可覆盖运行时、维护和模型/Provider 成本，受控写入和企业合规能力需要单独估算支持成本。不要承诺“完全自主”而没有将审批、异常处理和人工责任纳入产品。

## 构建不可替代性

模型可以替换，底层工具也可能替换；更难复制的是已验证的领域动作、数据质量规则、权限模型、评估集、审计记录和客户采用方式。Harness 的插件化结构使这些资产可以保持在业务层，而不与某个模型提供方或单一 UI 绑死。

建立可持续反馈闭环：收集真实失败与人工改写样本，按数据/策略/模型/交互分类，固定代表性样本为回放与验收用例，观察改动是否改善业务指标。不要只依赖离线 benchmark 或个别成功对话决定产品方向。

## 早期团队的技术优先级

第一阶段优先投入认证与租户、可靠 Provider、最小工具面、审批与审计、可观测性、可重放测试和客户配置。复杂多 agent 编排、自修改插件、大规模记忆、全自动写入和宽泛平台化通常应在一个流程的稳定价值被证实后再投入。

这不是降低技术标准，而是把技术能力用于缩短“客户问题—安全运行—可度量结果”的闭环。每一项新基础设施都应回答：它会让下一个客户更快上线，还是只让当前演示更复杂？
